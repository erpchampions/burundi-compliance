Fork Architecture Guide

A supplement to the upstream Burundi Compliance introduction. Read that first for the eBMS / OBR concepts; use this for what this fork changes.

1The key change: Sales Invoice customizations are detached

Upstream (Navari) injects OBR fields directly onto the Sales Invoice doctype via custom/sales_invoice.json — hundreds of custom fields (submission status, invoice identifier, eBMS signature, registered number/date).

This fork removes those fields from Sales Invoice and moves them into a dedicated OBR Invoice Submission doctype.

Why this matters Sales Invoice stays a stock, unmodified ERPNext doctype — no per-install custom-field churn and no migration risk when ERPNext changes Sales Invoice. All OBR state lives in one place, simpler to query and report on. The fork's sales_invoice.json is intentionally empty. 
{ "custom_fields": [], "custom_perms": [], "doctype": "Sales Invoice", "links": [], "property_setters": [] }

2The OBR Invoice Submission doctype

This is the fork's core record — one per submitted Sales Invoice / POS Invoice.

FieldTypePurpose
sales_invoiceLink (Sales Invoice)The source invoice (required)
payment_typeSelectCash / Bank / Credit / Others (required)
defer_submission_to_obrCheckSkip OBR on submit; send later
submitted_to_obrCheckeBMS Submission — OBR accepted it
ebms_invoice_cancelledCheckeBMS Invoice Cancelled
invoice_registered_noDataInvoice Registered No (from OBR)
invoice_registered_dateDateInvoice Registered Date (from OBR)
invoice_identifierDataInvoice Identifier (from OBR)
einvoice_signaturesSmall TexteBMS Signature (cryptographic)
reason_for_creditcancelText EditorReason for credit note / cancellation
amended_fromLinkSource record for amended / credit-note flows

Flow:

  1. User submits a Sales Invoice (or POS Invoice).
  2. doc_events → create_obr_submission fires and creates the linked OBR Invoice Submission.
  3. A Payment Type prompt appears (Cash / Bank / Credit / Others).
  4. The submission is queued to OBR in the background.
  5. OBR signs the invoice → the submission record is updated with the status fields above.
Where to check status Open the OBR Invoice Submission record — not the Sales Invoice. The upstream docs point at Sales Invoice fields; in this fork those fields no longer exist there.

3eBIMS Actions buttons

The eBIMS Actions buttons (Get Invoice, Re-Submit, Cancel Invoice in OBR) are driven by the associated OBR Invoice Submission record. If no submission record exists — e.g. a legacy invoice created before the app was installed — the buttons will not appear.

4Load-bearing config details

These match upstream, but two naming details are load-bearing in code and easy to get wrong.

Endpoint URLs must be named SandBox and Production

The doctype is autonamed format:{environment}, and get_urls() looks the record up by name:

# utils/utils.py
if environment == "sandbox":
    endpoint_doc = frappe.get_doc("eBMS Endpoint URLs", "SandBox")
else:
    endpoint = frappe.get_doc("eBMS Endpoint URLs", "Production")

Create two records, named exactly SandBox and Production, each with the six endpoints (login, add_invoice, get_invoice, cancel_invoice, check_TIN, add_stock_movement).

eBMS Settings is autonamed by Company

eBMS Settings is autonamed field:company — one record per company, looked up by company name. The TIN field on the settings form is read-only (fetch_from: company.tax_id); set the TIN on the Company doctype's Tax ID, not on the settings form.

TIN source of truth

The invoice payload reads the TIN from company.tax_id, not from eBMS Settings:

# utils/build_invoice_payload.py
company_tax_id = company.tax_id
...
"tp_TIN": company_tax_id,

5Version support

pyproject.toml declares frappe = ">=15.0.0,<17.0.0". Installed and migrated successfully on Frappe 15.110.0 (ERPNext 15). No v16-only APIs are used.

6Migration note for existing Navari installs

If you're migrating a site that previously used the upstream app (OBR fields on Sales Invoice):

  • The old Sales Invoice custom fields are not migrated into OBR Invoice Submission automatically.
  • Historical OBR submission state that lived on Sales Invoice will not appear in the new OBR Invoice Submission list.
  • Plan a data backfill if you need to preserve historical signing state.
